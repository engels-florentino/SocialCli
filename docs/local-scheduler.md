# Local queue supervision

Use the workspace root that contains the selected brand directory:

```sh
socialcli schedule-install --brand Example --root /absolute/workspace
socialcli schedule-doctor --brand Example --root /absolute/workspace --json
socialcli schedule-uninstall --brand Example --root /absolute/workspace
```

On macOS, installation registers a per-user LaunchAgent with an opaque label
computed from the canonical workspace path and the exact brand name. Separate
workspaces can use the same brand name without replacing each other's jobs.
Keep the interpreter used for installation available; replacing the environment
or moving the workspace requires reviewing the old installation first.

Installation enables only the exact owned job. It never boots out an existing
job to replace it. Existing configuration must match the current generated bytes,
be a regular file owned by the current user with mode `0600`, and have no symlinked
configuration ancestors. Modified or foreign files, unsafe log destinations,
and mismatching loaded jobs require manual review. A failed bootstrap can leave
the private configuration saved for diagnosis; it does not establish supervision.
Repeating installation for an unchanged matching job does not restart it.

Doctor requires exact saved configuration, matching loaded path, interpreter,
arguments, working directory, log destinations and 60-second interval, an
explicit enabled state, a successful last exit, and fresh healthy executor
evidence before reporting `ready`. Unknown or changed launchctl output stays
`attention_required`. Apple describes `launchctl print` as diagnostic output
rather than a stable API; supported fields may change with macOS.
The enabled-state probe accepts explicit `enabled`/`disabled` entries and the
boolean `false`/`true` disabled-state spelling; missing, duplicate or unknown
entries do not establish an enabled job. An idle
registered interval job need not have a running PID. A newly installed job can
remain unverified until its first successful execution. Inspect the selected
brand's `.socialctl/run-due.log` and `.socialctl/run-due.error.log` when needed.

`verified_now` is evidence about the current registration, not a promise of future
delivery. The Mac, original media, credentials, network and Python environment
must remain available. This GUI user agent requires the user to remain logged in;
intervals can be missed while the machine sleeps or the preceding run is still
active. `survives_logout` is therefore false. Linux user-timer and remote-executor
diagnostics retain their separate requirements.

Uninstall removes only the exact matching workspace/brand job and configuration.
It verifies registration removal before deleting the configuration. A cached job
whose ownership file is missing, an unknown manager response, or a mismatching
configuration is preserved for manual review. An already unregistered owned
configuration can be removed. Queue, media, credentials, logs and unrelated jobs
are preserved. Booting out a macOS agent can interrupt an active operation;
inspect its durable queue result before considering a retry.

## Explicit migration of a legacy macOS agent

Older versions used `com.socialctl.<lowercase-brand>.run-due`, shared across all
workspaces with that brand name. The current installer refuses installation
while that legacy file or registration exists. Doctor will not certify a new
job alongside a legacy job. Uninstall never removes the legacy job.

Migrate only after identifying its owner:

1. Inspect the legacy plist in `~/Library/LaunchAgents/` and its exact registration
   with `launchctl print gui/<uid>/<legacy-label>`. Verify the interpreter,
   `--brand`, canonical `--root` and working directory belong to the intended
   workspace. If ownership is different or uncertain, preserve it and resolve
   ownership before proceeding. Do not adopt it based on its label alone.
2. Choose a time when no approved operation is running. Record the legacy
   configuration and queue state. Explicitly boot out only that verified legacy
   service target with `launchctl bootout gui/<uid>/<legacy-label>`.
3. Confirm the exact job is absent from the available GUI domain. A connection or
   permission error is not proof of absence. Move only the verified legacy plist
   to a private backup outside `LaunchAgents`, without overwriting an existing
   backup. Do not remove queue, media or credentials.
4. Run `schedule-install` with the explicit intended workspace and brand. After
   the first successful tick, run `schedule-doctor`. Resolve any attention state
   before relying on unattended delivery. Never re-upload to repair an uncertain
   earlier publication.

If migration fails, retain both configuration records for diagnosis. Restoring a
legacy agent is a separate explicit operation after confirming the new exact job
is stopped and absent; never leave both supervisors active for the same queue.
